Install

The installer downloads the latest release for your OS and architecture, checks its sha256 and puts scalino in ~/.local/bin.

Scala Native links through clang, so Linux and macOS need clang on the PATH. The Xcode Command Line Tools have it; elsewhere it is apt install clang or the equivalent. Windows needs nothing: the first build downloads llvm-mingw.

Linux and macOS

curl -fsSL https://raw.githubusercontent.com/lolgab/scalino/main/install.sh | bash

Windows, from PowerShell

irm https://raw.githubusercontent.com/lolgab/scalino/main/install.ps1 | iex

Homebrew

brew tap lolgab/tap
brew install lolgab/tap/scalino

Debian and Ubuntu

curl -fsSLO https://github.com/lolgab/scalino/releases/download/vX.Y.Z/scalino_X.Y.Z_amd64.deb
sudo apt install ./scalino_X.Y.Z_amd64.deb

Fedora, RHEL and openSUSE

sudo dnf install https://github.com/lolgab/scalino/releases/download/vX.Y.Z/scalino-X.Y.Z-1.x86_64.rpm

Every release also has a plain tarball (a zip on Windows) for x86_64 and arm64. There are an AUR PKGBUILD and a Nix flake in packaging/, not published anywhere yet.

A small scala-cli

The commands are scala-cli's: run, compile, test, package, setup-ide, clean. So are the //> using directives and the flags, where scalino implements them. -w watches, --dep adds a dependency, and files under test/ are test scope.

What it doesn't give you is a choice of versions. A release is built from one Scala, one Scala Native and one Scala.js, and those are the ones you get (scalino version prints them). There is no JVM target either, so every dependency has to be published for Native or for JS.

Dependencies still come from Maven Central through coursier, whose cs launcher ships in the box.

// test/FibSuite.scala
//> using test.dep org.scalameta::munit::1.2.1

  test("fib(10) is 55"):
    assertEquals(fib(10), BigInt(55))
  test("fib(0) is 0"):
    assertEquals(fib(0), BigInt(0))

Also in the box

Macros run in an interpreter

dotc expands a macro by loading its bytecode into the compiler's own JVM. Here there is no JVM to load it into, so scalino interprets the macro's TASTy trees. Inline and quoted macros work, derivation such as jsoniter-scala's JsonCodecMaker.make included.

//> using dep com.github.plokhotnyuk.jsoniter-scala::jsoniter-scala-core::2.40.1
//> using compileOnly.dep com.github.plokhotnyuk.jsoniter-scala::jsoniter-scala-macros::2.40.1

case class Device(id: Int, model: String)
case class User(name: String, devices: Seq[Device])

given userCodec: JsonValueCodec[User] =
  JsonCodecMaker.make

The compiler stays warm

A background scalino-dotc keeps the compiler and your dependencies loaded between builds, and unchanged sources are reused. It exits after 15 idle minutes. These are Hello World on an M2 Pro: first build, after an edit, nothing changed.

# edit Hello.scala

Scala.js, also without a JVM

--js or //> using platform js builds the same sources for Scala.js. The linker is the Scala.js linker compiled with Scala Native, so all you need besides scalino is node to run the output. A native server can embed its Scala.js client with //> using jsClient.

$ scalino run --js Hello.scala
Compiling project (Scala 3.10.0, Scala.js 1.22.0)
Compiled project (Scala 3.10.0, Scala.js 1.22.0)

A language server, native as well

scalino-lsp sits on dotty's presentation compiler, the one Metals uses for Scala 3. Completion, hover, go to definition, references, rename, inlay hints, semantic tokens and code actions, with clients for Zed, VS Code and Neovim.

Packages without fpm

package --format wraps the binary as a tarball, a .deb, an .rpm, a Docker image or a Homebrew formula. The name, version and maintainer come from //> using package… directives.

$ scalino package Hello.scala --format tar,deb -o packages \
    --pkg-version 1.2.3 \
    --native-target-triple x86_64-unknown-linux-gnu,aarch64-unknown-linux-gnu

Builds that stay offline

scalino lock writes every jar's URL and sha256 to scalino.lock.json, and --offline builds from that and the local cache. The Nix flake fetches the locked jars itself, so a scalino program is an ordinary derivation.

# flake.nix
scalino.lib.${system}.mkScalinoApp {
  pname = "myapp";
  src = ./.;  # has scalino.lock.json
  nativeTargetTriples = [
    "x86_64-unknown-linux-musl"
    "aarch64-unknown-linux-musl"
  ];
}

Cross-compile from one machine

--native-target-triple takes a list. Every target is linked in the same process, so the program is read once.

The first time you name a target, scalino assembles its sysroot from upstream packages pinned by sha256. That takes curl and tar, and nothing is compiled. Cross links go through ld.lld, which scalino downloads if you don't have one.

The musl binaries are fully static, so one file runs on every distro. Tick some targets and see what you would run.
